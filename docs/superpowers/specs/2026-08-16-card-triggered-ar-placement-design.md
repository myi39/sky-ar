# sky-ar 再設計：カードをトリガーにした空間配置型 AR

日付: 2026-08-16

## 背景

現行の sky-ar は MindAR による画像トラッキング型 AR である。カードを認識している間だけ、その面を基準に 3D モデルが表示される。カードを画面から外すとモデルは消える。

この構造には自由度の限界がある。モデルはカードに縛られ、空間に置くことも、離れて眺めることもできない。

## 目的

カード認識を**アンカーではなくトリガー**として扱う構造に作り替える。カードから「どのキャラか」を特定したら、あとはそのモデルを**空間に自由に配置できる**ようにする。カードを片付けてもモデルは消えない。

### 非目的

- 複数キャラの同時配置、タップでの移動、独自演出（「置ければ十分」という要件）
- カード面へのモデルの位置合わせ（アンカーとしての役割は捨てる）
- 画像認識によるカード識別（初期スコープ外。後から足せる構造にはする）

## 前提と制約

| 項目 | 内容 |
|---|---|
| 対応端末 | iPhone 必須、Android も対応（両OS） |
| 作り込み | 「置ければ十分」 |
| 利用段階 | まず自分が試す段階。導入ハードルより最短で動くことを優先 |
| ビルド | なし。静的ファイルのみ（GitHub Pages がビルドを走らせないため） |
| 動作確認 | HTTPS 必須のため GitHub Pages（https://myi39.github.io/sky-ar/） |
| アセット | カード画像 38 枚、GLB 38 体。`<語幹>` で 1 対 1 対応 |

## 技術選定の根拠

空間トラッキング（SLAM・平面検出）は OS 側の機能（ARKit / ARCore）を借りないと実用にならない。2026 年時点でも、オープンソースのライブラリだけで iOS のマーカーレス空間トラッキングを実現する手段は事実上存在しない。

検討した選択肢:

| 案 | 判定 | 理由 |
|---|---|---|
| **OS の AR ビューアに委譲** | **採用** | 無料・両OS対応・精度最高。自前 UI は持てないが「置ければ十分」なら十分 |
| WebXR 自前実装 | 不採用 | iOS Safari が `immersive-ar` に非対応。Apple の対応予定表明もなし |
| 商用 WebAR プラットフォーム | 不採用 | 代表格の 8th Wall は 2026-02-28 にサービス終了済み。他は有料 |
| MindAR + IMU で擬似固定 | 不採用 | 位置トラッキングがなく、歩くとドリフトする |

したがって **iOS は AR Quick Look（`.usdz`）、Android は Scene Viewer（`.glb`）** に投げる。

## アーキテクチャ

入口とディスパッチャを分離する。中核は「ID を受け取って対応する 3D を AR ビューアに渡す」だけの薄い層であり、入口はそこに合流するだけの差し替え可能な部品とする。

```
入口A  NFC タグ          ─┐
       (URL に ?c=<id>)   │
                          │
入口B  一覧から選ぶ        ─┼→ キャラID ─→ ディスパッチャ ─→ AR ビューア
       (画像グリッド)      │              (端末判定)      iOS: .usdz
                          │                              Android: .glb
入口C  画像認識（将来）    ─┘
```

URL が状態を持つ。`?c=<id>` があれば個別画面、なければ一覧。この 1 本の分岐で入口 A/B の両方をさばく。将来 C を足しても中核は変更不要。

### 識別子

`<id>` は `01_Mob` のような語幹で、画像・GLB・USDZ の 3 つを貫く唯一のキーとする。

- 番号（`00`〜`36`）は**一意ではない**（`00_andI` と `00_andYou1` が両方 `00`）。ID は必ず語幹全体を使う
- 全ファイル名は ASCII のみ、画像とモデルで大文字小文字まで完全一致させてある（GitHub Pages は大小を区別するため）

## リポジトリ構成

```
sky-ar/
├── index.html              ページの骨格と CSS。ロジックは持たない
├── app.js                  URL 分岐・一覧描画・個別画面描画・端末判定
├── cards.js                カード ID の配列だけを持つ生成物
├── images/
│   ├── <id>_front.jpg      カード画像 38 枚（7.6MB）
│   └── thumb/<id>.jpg      一覧用サムネイル 38 枚（新規生成・約 1MB）
├── 3d/
│   ├── glb/<id>.glb        Android 用 兼 USDZ 変換元 38 体（80MB）
│   └── usdz/<id>.usdz      iOS 用 38 体（約 80MB）
├── tools/
│   ├── glb2usdz.py         Blender 変換スクリプト（GLB 1 体 → USDZ 1 体）
│   ├── build_usdz.ps1      3d/glb/*.glb を全て 3d/usdz/ へ変換
│   ├── make_thumbs.ps1     images/*_front.jpg から images/thumb/ を生成
│   ├── make_cards.ps1      3d/glb/ の一覧から cards.js を生成
│   └── verify.ps1          ファイル数・命名・対応関係の不変条件を検査
└── docs/superpowers/
    ├── specs/              本書
    └── plans/              実装計画
```

USDZ はリポジトリにコミットする（GitHub Pages はビルドを走らせないため）。結果としてリポジトリは約 170MB になる。GitHub Pages の上限 1GB には余裕がある。ユーザーが 1 回の AR 起動で落とすのは約 2MB。

一覧で元のカード画像（各 200KB）を 38 枚並べると初回 7.6MB になるため、サムネイル（各 30KB 程度）を別途生成する。元画像は個別画面で使う。

サムネイルは `tools/make_thumbs.ps1` が .NET の `System.Drawing` で生成する（追加インストール不要）。出力先は `images/thumb/<id>.jpg`（`_front` は付けない）、幅 320px の JPEG。

テクスチャは**原寸（830×1185）を維持**する。Blender の `usdz_downscale_size` で縮小できるが、画質を優先する。変換はスクリプト化されているため、後から一括で焼き直せる。

## 変換パイプライン

`tools/glb2usdz.py` を Blender 5.1 のバックグラウンドモードで実行する。

```
blender -b --factory-startup --python-exit-code 1 --python tools/glb2usdz.py -- <src.glb> <dst.usdz> 0.15
```

1 体あたり 0.3〜1.4 秒。38 体で 1 分未満。

### 処理内容

1. **GLB を読み込む**
2. **テクスチャを ASCII 名でディスクに書き出す** — バックグラウンドモードでは GLB のテクスチャが遅延ロードのままで `img.save()` が空振りする（`has_data` が False）。`img.packed_file.data` から生バイトを直接取り出し、マジックバイトで拡張子を判定して保存する。この処理がないと USDZ にテクスチャが同梱されず、AR Quick Look で真っ白になる
3. **実寸に正規化** — 最長辺が 0.15m になるようスケール。カードは概ね 10.3 × 1.0 × 15.0 cm になる
4. **マテリアル調整**（下記）
5. **USDZ として書き出す** — `convert_orientation=True` / `export_global_up_selection='Y'` / `export_global_forward_selection='NEGATIVE_Z'`（AR Quick Look は Y-up、Blender は Z-up）、`convert_scene_units='METERS'`、`generate_preview_surface=True`、`export_textures_mode='NEW'`

### マテリアル調整の規則

全 38 体で構造が完全に一致していることを実測で確認済み（下記「調査結果」参照）。

- **全レイヤー**: 発光を除去（Emission Strength 0 / Emission Color 黒）、Metallic 0
- **奥行き順で手前 2 枚**（`星`・`本体`）: `IOR` を 1.0、`Roughness` を 1.0 に。ほぼ全面が透明なレイヤーであり、鏡面反射が白いモヤとして見えるため
- **残り 3 枚**（`マテリアル`/`後ろ`・`側面`・`裏`）: 既定のまま（IOR 1.5 / Roughness 0.5）。反射を残す

判定は**位置ベース**（最薄軸に沿った奥行き順の前 2 枚）とする。透明率による判定でも 38 体すべてで同じ結果になるが、位置の方が意図が明示的で想定外の挙動が起きにくい。

**防御**: 「メッシュ 1 個・マテリアル 5 枚」の条件から外れるモデルが来た場合は警告を出してそのモデルをスキップする。将来モデルを追加したとき、誤ったレイヤーをマット化して黙って壊れることを防ぐ。

## `index.html` の挙動

```
URL に ?c=<id> があるか
├─ ない  → 一覧（38 枚のサムネイルグリッド）
│           各サムネイルは <a href="?c=01_Mob"> のただのリンク
│           JS 不要。戻るボタンも自然に効く
│
└─ ある  → 個別画面（カード画像 + 「AR で表示」ボタン）
            端末判定して起動先を切り替える
            ├─ iOS     : <a rel="ar" href="3d/usdz/<id>.usdz"> （子に <img> が必須）
            ├─ Android : Scene Viewer の intent URL（3d/glb/<id>.glb を絶対 URL で指定）
            └─ その他   : カード画像のみ表示 + 非対応の案内
```

JS は端末判定の数行のみ。外部ライブラリはゼロ。MindAR・A-Frame・Three.js への依存が全て消え、CDN 読み込みのない静的サイトになる。

**制約**: iOS も Android も AR の起動には**ユーザーのタップが必要**で、ページを開いた瞬間に自動で AR ビューアを立ち上げることはできない。NFC 経由でも「かざす → ページが開く → ボタンを 1 回押す」の 3 手になる。回避不能。

## NFC タグの運用

タグに書くのは URL 1 本のみ。

```
https://myi39.github.io/sky-ar/?c=01_Mob
```

iPhone は OS がタグを読んで通知バナーを出し、タップで Safari が開く。**こちら側に NFC 用のコードは一切不要**。Android も同じ挙動。Web NFC API（Chrome on Android 限定）は使わない。

書き込みは市販アプリ（NFC Tools 等）で手作業。38 枚なら 10 分程度。書き込み用ページは作らない。

## 調査結果（実測）

### 全 38 体のレイヤー構造は一致している

```
全 38 体: メッシュ 1 個 / マテリアル 5 枚 / 最薄軸 = Y
奥行き順（手前→奥）: 星 > 本体 > (マテリアル|後ろ) > 側面 > 裏
```

差異は 3 枚目の名前だけ（`マテリアル` が 18 体、`後ろ` が 20 体。17 番以降で改名）。位置も役割も同じ。

| 層 | 名前 | 透明率 | 処理 |
|---|---|---|---|
| 1（手前） | `星` | 99〜100% | マット化 |
| 2 | `本体` | 58〜80% | マット化 |
| 3 | `マテリアル` / `後ろ` | 13〜32% | 反射維持 |
| 4 | `側面` | テクスチャなし | 反射維持 |
| 5（最奥） | `裏` | 0〜15% | 反射維持 |

`星` は 38 体すべてで発光がオン（Emission Strength 1.0・発光色は白）。

### MindAR は 38 枚では成立しない

- 手元の `image_andi.mind` は 1 枚で 984KB
- 報告例では 6 枚で 32MB に膨張
- MindAR には「多ターゲットでモバイルブラウザがクラッシュする」Issue がある

カードをアンカーとして追跡する必要がなくなった以上、MindAR を使う理由自体がない。必要なのは「どのカードか 1 回当てる」ことだけで、追跡は不要。

### USDZ の透過に関する仕様上の落とし穴

UsdPreviewSurface では、**opacity は diffuse 成分しか減衰させない**。emissive と specular は不透明度に関わらず全重量で残る（ガラスを想定した設計）。透明な板が見えてしまう原因はここにある。

- `星` の発光（白・強度 1.0）が板の全面を光らせていた → 発光を除去して解消
- `inputs:specular` は **UsdPreviewSurface の正式な入力ではない**。Blender が独自に書いているだけで RealityKit は読まない。0 にしても効果はない
- 実際の鏡面反射は metallic ワークフローにおいて `ior` から導出される

### 三者の変換ツールについて

- **three.js `USDZExporter` は使えない** — iOS の AR Quick Look で透過が失われる既知の問題がある。本プロジェクトのモデルは透過平面の積層そのものなので致命的
- **Reality Converter は Mac 専用**
- **Blender CLI は使える**（本書の変換パイプライン）

### 6 月から未解決だったレイヤー逆転バグの原因

モデルは**メッシュ 1 個に 5 マテリアル**が乗った構造である。three.js の `renderOrder` は**メッシュ単位**にしか効かないため、1 メッシュ内の 5 マテリアルには適用されない。`renderOrder` をいくら調整しても変化しなかったのはこのためである。

新アーキテクチャでは描画を RealityKit / Scene Viewer に委ねるため、この問題自体が消える。実機確認でもレイヤー順は正しく描画された。

## 未解決の課題

**透明レイヤーにごく薄い反射が残る。** `ior` を 1.0 にしても解消しなかった。RealityKit が誘電体の反射率を 0.04 に固定していて `ior` を参照していない可能性があるが未検証。

現時点では**許容する**（実用上ほとんど気にならないレベルという判断）。変換がスクリプト化されているため、後から方針を変えて 38 体を一括で焼き直せる。

未検証の対処法:

- `useSpecularWorkflow=1` + `specularColor=(0,0,0)` — `ior` 経由でなく反射色を直接ゼロ指定する。副作用なし。ただし Blender が書き出さないため `.usda` の後処理が必要
- `opacityThreshold` を立てる — 確実に消えるが、アルファが二値化してキラキラの輪郭がギザつく

## 将来の拡張

**画像認識による識別（入口C）。** MindAR は使えないが、カードが「トリガー」に徹する以上、必要なのは追跡ではなく識別のみである。

- 案: ガイド枠 + 知覚ハッシュ。38 枚分の指紋は合計数百バイトで済む。外部ライブラリ不要
- 実装前にオフラインで識別性能を測定できる（カード画像 38 枚が手元にあるため）
- 精度不足の場合は MobileNet の特徴ベクトル（TensorFlow.js、モデル 5〜16MB）に移行

いずれの場合も、ID を確定させて既存のディスパッチャに渡すだけなので中核の変更は不要。
